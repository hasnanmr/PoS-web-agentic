# Screen → endpoint map (wireframe contract)

Status: **draft v1 — 2026-11-17**. Source: `design/SME-POS-Wireframe.figcraft` (screens O1–O17, S1–S12, M1–M6, K0–K4, Q1–Q5, C1–C15) and `design/WIREFRAME-TRACEABILITY.md`.

**Rule:** every backend endpoint used by the admin app or the attendance tablet must serve exactly what its wireframe screen shows and does: the same fields, filters, actions, and error states. When a screen needs data, add it to the endpoint listed here; when an endpoint is added or changed, update this table in the same change. A screen that is not drawn gets no endpoint until it is designed (or the product owner approves it).

Conventions (from `api-boundaries.md`): base `/api/v1`; `owner/*` = owner only, `ops/*` = owner + staff (assigned outlets only), `device/*` = attendance tablet session, `public/t/{token}/*` = customer web chat from a table QR (no login, scoped by the table token), `public/o/{slug}/*` = customer web chat from the outlet link (no login, scoped by the outlet slug; planned, T-141). Money in integer rupiah, enums as in T-001, times with offset plus `outlet.timezone`. Mobile screens (M1–M6) use the **same endpoints** as their desktop screens; only the layout changes.

Every list/action response for an order includes **`allowed_actions`**, computed by the server from the order's flow (channel, payment mode, status, payment status). The UI only renders buttons from this list (S2 note: "Tombol aksi hanya menawarkan transisi valid").

### O2 · Dashboard — tab Ringkasan + keramaian (T-071, T-123, T-124)

The Dashboard header has two tabs: **Ringkasan** (this section) and **PO & Supplier** (O17 cards + O15 list, below). Each tab keeps its own filters; the PO tab's figures are not in `GET /owner/dashboard`.

| Card | Endpoint | Query / fields |
|---|---|---|
| All cards | `GET /owner/dashboard` ✅ implemented | Query: `outlet_id` (or all), `period=today\|week\|month\|range` (default `today`; week = from Monday, month = from the 1st, both up to today), `hours=all\|busy\|quiet` (default `all`). **`period=range`** (header "Rentang ▾", a date picker like O9) needs `from` and `to` (`YYYY-MM-DD`, outlet-local days): `from ≤ to`, at most 92 days, `to` not after today; otherwise `422 validation_failed` with `details.field`. A range compares with `previous_period` (same rule as O9: a range from the 1st with the same days of the previous month(s), any other range with the same number of days right before it). Periods are each outlet's own local days. Also returns `period`, `from`, `to` (the days used, in the first selected outlet's zone), `hours`, `as_of` (server time, for "Pukul 12.40"). |
| KPI tiles | ↳ `kpis` | `revenue_excl_pb1` (ledger revenue minus the menu part of refunds) + `change_pct` vs the previous period (yesterday / the same days last week / the same days last month; `null` when that period had none), `orders` + `cash_count` + `qris_count` (paid orders, not cancelled; open-bill orders take their bill's payment method), `pb1_collected` (ledger PB1 minus PB1 refunded), `delivery_fee` (minus delivery fees of refunded orders) + `delivery_orders`. **One time basis for every card: the outlet-local time the order was created** (product owner decision 2026-11-20). Money comes from the ledger, but each row is dated by its order's creation time (an open bill's rows by the time the bill was opened), and a refund lowers the day of the order it refunds; so around midnight O2 can differ from O9, which follows the payment date. A refund row (order total) is split into menu revenue, PB1 (`pb1_portion`) and the order's delivery fee. |
| Peta keramaian (day × hour, 4 weeks) | ↳ `busyness_map` | `[{weekday (ISO, 1 = Sen), hour, avg_orders}]`: paid orders per weekday and outlet-local hour over the last 28 complete days ÷ 4, summed across the selected outlets. Cells: opening hours (any selected outlet open) plus any cell that had orders; every such cell is returned, including 0. Hours after midnight are drawn after the evening (columns start after the longest closed stretch). Not affected by `period` or `hours`. |
| Keramaian outlet sekarang | ↳ `current_crowd` | `[{outlet_id, name, timezone, occupied_tables, total_tables, active_orders, level: ramai\|normal\|sepi}]`. Occupied = active table with a seated reservation, an open bill, or an active order, each started in the last 12 hours (so a table nobody closed does not stay occupied). Active order = `confirmed`, `preparing`, `ready`, or `out_for_delivery`, created in the last 12 hours. Level (placeholder thresholds, `app/core/dashboard.py`): occupied ≥ 75% → ramai, ≤ 30% → sepi; an outlet without tables compares active orders with the busyness-map average for this weekday and hour (≥ 130% ramai, ≤ 60% sepi). The card shows "Pukul …" in the outlets' zone (WIB plus each other zone's own time when zones differ). Not affected by `period` or `hours`. |
| Order per jam | ↳ `orders_per_hour` | `[{hour, orders, mark: busy\|quiet\|null}]` + `busy_summary`, `quiet_summary` (`{hours[], orders, share_pct}`). Paid orders per outlet-local creation hour over the period. Shown hours: opening hours plus any hour that had orders (so busy + normal + quiet add up to the KPI); on the outlet's today, opening hours that have not started yet are left out. Hours after midnight follow the evening (18 … 23, 00, 01). Busy ≥ 130% of the average per shown hour, quiet ≤ 60% (T-123 placeholders). The chart itself is not filtered by `hours`; the `hours` filter uses these marks to filter the KPI tiles, channel mix, and payment methods, all by the order's creation hour. |
| Stok rendah & sold out | ↳ `low_stock` | `[{stock_item, outlet_id, outlet, on_hand, low_threshold, unit, display_unit, status: low\|out}]`, sold out first, then by name; `out` at 0, `low` at or below the threshold. Only items the outlet carries (an `outlet_stock` row): an item never stocked at an outlet is not listed as sold out there. `display_unit` added so the card shows "0,8 L" like S7. Not affected by `period` or `hours`. |
| Komposisi per kanal / Metode bayar | ↳ `channel_mix`, `payment_methods` | `[{channel, orders, share_pct}]` for `web_online`, `web_table`, and `counter` always, plus `whatsapp_online`/`whatsapp_table` only when they have orders (Phase 3), so the shares cover every paid order. Labels and series colors as on the O2 wireframe (#85): Web chat (link outlet) `#1E4FA3`, Web chat (QR meja) `#8FB0E8`, Counter `#CBD5E6`; the O2b "Semua kanal ▾" filter uses the same labels; `[{method: cash\|qris, amount, transactions}]`: amount = ledger revenue + PB1 + delivery fee minus refunds paid with that method, transactions = payments; both dated by the order's (or bill's) creation time like the KPI tiles. |
| Item terlaris (own toggle Hari ini / Bulan ini / Tahun ini) | `GET /owner/dashboard/top-items` ✅ implemented | Query: `outlet_id` (or all, from the header), `period=day\|month\|year` (default `day`). Own endpoint because the card has its own period toggle and ignores the header's `period` and `hours`. → `{period, top_items: [{product_id, name, quantity_sold, revenue}]}` (`product_id` lets a row open O2b for that item), at most 5, sorted by `quantity_sold` desc, then `revenue` desc. Today / this month / this year in each outlet's time zone, by order `created_at`. Paid orders only (`payment_status = paid`, not cancelled; reversed orders are `refunded` and drop out); add-on variants are grouped under their menu item; `revenue` = sum of `order_items.line_total` (incl. add-ons, excl. PB1 and delivery fee, integer rupiah); `name` = current product name. Empty list → "Belum ada item terjual di periode ini." No migration needed (`order_items` already stores quantity and line_total). |

Staff calling it → `403` (AC7.7).

### O2b · Dashboard — drawer detail Revenue / Order (drill-down from O2)

A drawer from the right over O2 (same pattern as S3), opened by: the **Revenue** tile, the **Order** tile, a bar in **Order per jam**, or a row in **Item terlaris**. It lists the paid orders behind that number, so the drawer total equals the figure that was clicked.

| Part | Endpoint | Query / fields |
|---|---|---|
| Whole drawer | `GET /owner/dashboard/orders` | Query: `outlet_id` (or all), `period=today\|week\|month\|year\|range` (+ `from`, `to` for `range`, same rules as O2), `hours=all\|busy\|quiet` (default `all`), `hour` (0–23, a bar of Order per jam), `product_id` (a row of Item terlaris), `method=cash\|qris` (chip), `channel=whatsapp_online\|whatsapp_table\|web_table\|counter` (Kanal ▾), `q` (order number, "1036" or "A-1036"), `cursor`, `limit` (default 30, max 100). Tiles send the header's outlet, period, and hours; a bar sends `hour` with `hours=all` (the chart is not filtered by hours); an item row sends `product_id` and the card's own period (`day` → `today`, `month`, `year`) with `hours=all`. Staff → `403`. |
| Ringkasan box | ↳ `summary` | `{orders, revenue_excl_pb1, cash_count, qris_count}`: paid orders (`payment_status = paid`, not cancelled) in the period, by the outlet-local time the order was created (same basis as O2); `revenue_excl_pb1` = sum of `orders.subtotal` (excl. PB1 and delivery fee). A reversed order is `refunded` and drops out, as on O2. Follows period, hours, hour, and product; **not** the chips, Kanal, or search, so the chip counts "Semua 109 · Cash 38 · QRIS 71" stay put while the list is filtered. |
| Item (from Item terlaris) | ↳ `item` | `{product_id, name, quantity, revenue}` when `product_id` is given (same numbers as the Item terlaris row), else `null`. |
| Per outlet | ↳ `by_outlet` | `[{outlet_id, name, orders, revenue_excl_pb1}]`, same scope as `summary`, largest revenue first. Shown only for "Semua outlet" with more than one outlet. |
| Daftar order | ↳ `orders`, `next_cursor` | `[{id, order_no, outlet_id, outlet, timezone, created_at, channel, type, table, customer_name, payment_method, item_summary, revenue_excl_pb1, total}]`, newest first; every filter applies. "Muat lagi" sends `next_cursor`. A row opens S3 (`GET /ops/orders/{id}`) inside the same drawer with "← Kembali". Empty → "Belum ada order di periode ini." |

No migration: `orders`, `order_items`, and `payments` hold everything (payment method as on O2: an open-bill order takes its bill's payment).
